## 1. 项目目标

通过自然语言统一调度模特套图生成与虚拟试衣，完成需求澄清、素材复用、选图、批量执行、进度查询及结果交付。

第一版主要交付可独立运行、调用和测试的 Agent 功能逻辑。前端暂不开发，通过命令行／脚本验证完整交互，再由未来的前端或其他调用方接入。

## 2. 已确认的技术选型

| 组成 | 选型 | 职责 |
| --- | --- | --- |
| 开发语言 | Python | 实现业务逻辑与服务调用 |
| 流程编排 | LangGraph | 管理节点、分支、等待与恢复 |
| 数据定义与校验 | Pydantic | 约束输入、模型解析结果与工具数据 |
| 本地存储 | SQLite | 保存会话、素材索引、任务、选择及流程检查点 |
| 主控大模型 | 千问 `qwen3.8-flash`，百炼北京地域 | 理解中文需求、提取操作、澄清问题与组织回复 |
| Agent 结构 | 一个主 Agent ＋ 两个图像工具 | 套图生成、虚拟试衣分别作为工具 |

模型名称、接口地址和鉴权配置独立管理，保留后续替换模型的能力。Pydantic 负责结构校验，素材是否存在、编号是否有效、人物是否对应等语义规则由业务代码校验。

具体 Python 版本及依赖兼容版本在启动开发时检查环境后确定并锁定。本计划不假定依赖已经安装，也不将更换模型等同于业务流程已验收。

## 3. 已确认的业务规则

### 3.1 必需输入与追问

| 功能 | 必需输入 | 缺少输入时 |
| --- | --- | --- |
| 模特套图生成 | 描述希望生成的模特图的文字 | 追问模特图的文本描述 |
| 单次虚拟试衣 | 一张服装图 ＋ 一张模特图 | 只追问缺少的图片 |

- 套图生成不要求用户先上传模特图。
- 数量、画幅等沿用既有套图 API 的默认设置，不增加为用户必填项。用户主动提出相关要求时先记录，真实 API 是否支持透传在对接时核对。
- 图片用途必须明确。可以依据用户明确的文字或上传角色确定；用途／指代有歧义时追问，不按上传顺序猜测。
- 当前消息未提供的素材，可以从当前会话中复用已明确用途和对象的素材。
- 补齐后沿用原有需求继续执行，无须用户重新描述全部内容，也不增加一次通用确认步骤。

### 3.2 选择与批量处理

- 支持选择单张、多张或整组图片。
- 图片组、图片和任务都有持久化标识；展示编号不随排序、筛选或重启改变，也不回收复用。
- “第 1 张”“这件”“这组”等表达只在上下文唯一时解析，否则澄清对象。
- 单次试衣严格是一张模特图加一张服装图。批量试衣拆为多个子项，每个子项单独记录输入与结果。
- 一张服装图可复用于多张模特图；出现多件服装且配对关系不明确时，先澄清配对，不默认执行所有组合。
- “整组”在提交时固定为明确的图片集合，之后产生的新图不自动加入该任务。
- 单纯选图保存选择；如果此前已经明确要求“选完后穿衣”，且输入齐全，则继续待执行的穿衣步骤。用户明确说“只选图，暂不执行”时继续等待。

展示编号可采用 `G001-001`（套图组中的一张图）、`T001-001`（试衣组中的一张结果）等形式。比如选中 `G001-001` 与 `G001-003` 后穿衣，两张新结果分别记录各自的输入编号，不能按“新结果的第几张”倒推人物对应关系。具体展示格式在实现阶段统一，编号固定的规则不变。

### 3.3 组合流程与继续换衣

- “先生成套图，再穿这件”未明确范围时，生成后等待用户选图。
- 用户明确“全部穿衣”时，套图生成成功后自动处理整组。
- 用户明确“等我选”时，在选图节点等待，不提前提交穿衣任务。
- 再次换衣默认使用该结果对应的原始模特图；用户明确指定某张结果图作为输入时，使用指定图。
- 模特原图和已有结果始终保留，换衣及调整产生新的任务与结果。
- 批量部分失败时保留成功结果，展示失败项，由用户决定是否重试失败项。
- 重试失败项时保留原子项编号，新增执行尝试记录；已成功子项不随之重复执行。

“原始模特图”指该条换衣链路起点的模特图片：既可以是上传的模特图，也可以是某张套图结果。套图中的不同姿势图片各自保留对应的起始图，不能统一指向同一张图。

### 3.4 调整需求

记录每次执行时的需求快照。用户调整描述、服装或目标图片时，创建新需求版本或新任务，既有结果的输入解释保持不变。运行中的任务不被一条新消息静默改写。

## 5. 两个图像工具的边界

真实 API 文档不作为开发其他业务逻辑的前置条件。先定义工具的业务输入输出，再在后续对接时转换为已有 API 的格式。

| 工具 | 业务输入 | 输出需要表达的信息 |
| --- | --- | --- |
| 套图工具 | 模特图文本描述；内部请求标识 | 服务任务标识、执行状态、结果图片列表或失败信息 |
| 单次穿衣工具 | 一个模特素材引用、一个服装素材引用；内部请求／子项标识 | 服务任务标识、执行状态、对应结果图片或失败信息 |

内部追踪标识由系统生成，不要求用户提供。素材引用由适配层解析成真实 API 需要的路径、URL 或文件形式。

执行层需要区分提交与查询。真实服务同步返回时可直接记录终态；异步返回时保存服务任务标识，再通过查询或回调推进状态。不让一次大模型调用一直等待图像任务完成。

空壳与模拟必须清晰区分：

- 默认空壳明确返回“服务尚未接入”的结构化状态／错误，不返回空结果假装成功。
- 只有显式开启 Mock 才使用模拟能力；模拟任务与结果带有模拟标记，完成状态与真实成功区分。
- 模拟可使用带标记的测试素材验证流程和对应关系，不冒充真实生成的模特或穿衣图片。
- 测试素材不能被自动传给未来的真实图像 API。
- 没有真实图片时，不声称已经完成真实图片保存、预览或下载。

## 6. 对外输入输出约定

以下是拟议的业务约定，实际字段与函数签名在实现阶段细化。

### 输入

- 会话 ID：首次交互可由系统创建；后续用于继续同一上下文。
- 用户文字：需求、补充信息、图片选择、进度查询或调整指令。
- 附件引用：新上传或已有素材的标识／位置，以及明确的图片用途。

文字或附件至少提供一种。原始文件与文字上下文分开保存，模型需要看图时再按需传入图片。

### 输出

- 回复类型：需要补充信息、任务已提交、执行中、等待选图、完成、部分完成、失败或工具未接入。
- 用户可读说明：明确当前发生什么、缺什么或等待什么。
- 定位信息：会话 ID、任务 ID、图片组与稳定图片编号。
- 结果列表：图片引用、来源模特、服装、逐项状态及可用文件位置。
- 后续可执行操作：补充素材、选图、查询、继续换衣、重试失败项或获取已保存结果。
- 模式标识：真实调用或模拟，避免混淆。

前端暂不实现；预览／下载能力先体现为真实可用文件的保存、定位和导出方法。HTTP 下载链接、图片卡片和按钮由未来的服务层／前端提供。

## 7. 核心数据与状态

### 需要保存的数据

| 对象 | 主要内容 |
| --- | --- |
| 会话 | 对话记录、当前需求、当前素材组、选择及等待的输入 |
| 素材 | 图片标识、用途、来源、文件位置、展示编号及模拟标记 |
| 需求版本 | 描述、目标图片、服装以及本次执行时的参数快照 |
| 流程记录 | 多步骤计划、已完成步骤、下一步及等待原因 |
| 任务／子项 | 状态、请求标识、供应商任务标识、逐项输入、结果及错误 |
| 选择集 | 明确的图片 ID 集合、来源图片组与选择时的上下文 |

每个试衣结果必须能找到：本次实际输入的模特图、对应原始模特图、直接父素材、实际服装图、来源任务及需求版本。按 ID 关联，不依赖供应商返回数组顺序。

### 分开记录三层状态

| 层级 | 建议状态 | 例子 |
| --- | --- | --- |
| 会话中的操作流程 | 待补充信息、可执行、执行中、待选图、完成、部分完成、失败 | 套图已完成，流程仍在等待用户选图 |
| 具体任务／子项 | 待提交、排队、执行中、成功、部分成功、失败、结果待核实、模拟完成 | 某次穿衣 API 正在执行，另一个子项已成功；部分成功用于汇总任务 |
| 工具可用性与模式 | 未接入、Mock、真实服务 | 输入已齐全，但当前只有工具空壳，不能标记为真实生成成功 |

“需要用户补图”和“图像工具未接入”分别展示，不能通过让用户反复补素材解决服务未配置问题。

SQLite 保存业务数据与 LangGraph 持久化检查点，两者关联但职责分开。素材、任务和输入结果对应记录作为业务事实，流程检查点引用相应 ID；恢复时校验两者一致，避免重复提交或状态分叉。图像文件保存在受管理的素材目录，数据库保存索引，不将图片二进制或大段 base64 写入聊天记录／流程状态。

## 8. 节点与流转规则

| 节点 | 处理内容 | 下一步 |
| --- | --- | --- |
| 接收消息 | 关联会话、记录文字和附件 | 理解本轮意图 |
| 理解意图 | 结合上下文解析操作、对象和是否继续已有流程 | 校验输入，或直接进入选择／进度查询 |
| 校验输入 | 检查描述、人物图、服装图、选择与配对 | 缺失则追问；齐全则进入相应操作 |
| 追问与等待 | 保存已知内容和明确的缺失项 | 新消息到来后只补齐缺失部分 |
| 套图生成 | 调用套图工具，记录任务／结果 | 按用户指令交付、等待选图或继续整组穿衣 |
| 等待选图 | 展示固定编号并保存后续计划 | 选择齐全后继续；进度查询不会误当作选图答案 |
| 虚拟试衣 | 固定选区与输入，拆为逐张子项 | 查询状态、汇总逐项结果 |
| 查询进度 | 读取已有任务，必要时查询工具状态 | 回复状态；不重复创建生成任务 |
| 结果交付 | 汇总结果、来源、保存状态及可用文件 | 接受继续选图、换衣或调整 |

关键分支：

1. 只生成套图：文本描述齐全 → 提交生成 → 返回结果。
2. 直接穿衣：人物图与服装图齐全 → 提交穿衣 → 返回对应结果。
3. 先生成、后选图穿衣：生成 → 待选图 → 选择与服装齐全 → 穿衣。
4. 先生成、全部穿衣：生成成功 → 固定整组选择 → 逐张穿衣。
5. 后续换衣：定位目标及原始模特图 → 解析新服装 → 新建任务，保留已有结果。

前一步部分失败时，本计划建议先展示成功项与失败项，再由用户选择补齐后继续或仅处理成功部分，避免把“整组”静默缩减为部分图片。

图像调用与等待用户的节点分开，确保恢复选图时不重复执行前面的生成步骤。相同会话的状态更新需要避免并发消息互相覆盖。

## 9. 开发阶段与交付物

按依赖顺序推进；各阶段完成相应验证并汇报后，再继续后续工作。不能把其中一个接口跑通视为整个 Agent 已完成。

| 阶段 | 主要工作 | 交付物与通过条件 |
| --- | --- | --- |
| P0：计划审阅 | 用户调整范围与行为，明确开始开发 | 形成实施基线；当前仅完成计划初稿 |
| P1：工程与数据基础 | 核对环境；组织 Python 项目；定义数据模型；实现 SQLite 素材／会话／任务存取 | 可运行的基础模块；保存并重新加载后编号和来源不变 |
| P2：业务规则与工具空壳 | 输入缺失计算；素材复用；选图和换衣基准解析；实现两个工具接口与 Mock | 可独立测试规则；未接入与模拟状态清晰；逐项对应正确 |
| P3：流程与任务编排 | 使用模型替身驱动 LangGraph；实现节点、等待与恢复、组合操作、批量状态、进度查询和重复提交防护 | 离线跑通四条主要流程；重启可恢复；查询／恢复不会重复生成 |
| P4：主控模型接入 | 模型配置、千问适配、结构化意图解析、追问和回复；接入已验证的业务流程 | 相同业务结构可使用真实模型或测试替身；非法／歧义输出不直接执行工具 |
| P5：结果交付与调用入口 | 结果清单、来源映射、文件保存与定位、继续调整；命令行／脚本入口 | 无前端可演示多轮流程；真实测试文件可保存与导出，Mock 输出明确标记 |
| P6：联调与验收 | 回归测试、异常与恢复场景、配置和运行说明 | 全部本期逻辑验收场景通过；说明真实图像能力仍待接入 |
| 后续：真实图像服务 | 替换适配器、真实素材联调、图像保存及视觉质量测试 | 单独验收真实套图／穿衣能力及完整真实图像交付 |

每个阶段随实现增加必要测试；P6 负责完整回归，不将所有测试推迟到最后。

启动开发时先阅读并评估目录中现有的 `main.py`，保留用户已有内容和 `.idea` 配置，不默认覆盖。项目目录按第 13 节已确认的目标结构分阶段创建，当前不预先创建代码文件。

## 10. 验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| A01 | 用户只有“帮我生成套图”，未给模特图描述 | 追问文本描述，不要求上传模特图 |
| A02 | 只有完整的模特图文本描述 | 可进入生成，不因缺少数量／画幅而阻塞 |
| A03 | 穿衣已有模特图，缺少服装图 | 只追问服装图；补齐后沿用原任务需求 |
| A04 | 穿衣两种图片均缺少 | 一次说明需要的两种图片，允许分多轮补齐 |
| A05 | 图片存在但用途或指代不明 | 澄清对应关系，不按上传顺序猜测 |
| A06 | 当前消息没附图，会话中已有明确素材 | 复用已有素材，不重复要求上传 |
| A07 | 生成结果重新排序，或程序重启后查看 | 图片编号与素材绑定不变 |
| A08 | “先生成，再穿这件”，未指定范围 | 生成后进入待选图；生成任务本身已完成 |
| A09 | “先生成，全部穿这件” | 正常生成完成后固定整组，逐张提交穿衣 |
| A10 | 选择第 1、3 张后执行穿衣 | 仅处理这两张，结果分别关联正确输入 |
| A11 | 单纯选图，未要求执行且没有待续接指令 | 只保存选择，不新建图像任务 |
| A12 | 多人多件服装、配对不明 | 追问配对，不自动执行所有组合 |
| A13 | 对某结果说“再换另一件” | 默认使用对应原始模特图，保留之前结果 |
| A14 | 明确说“用这张结果图继续换衣” | 实际输入是指定结果图，同时保留来源链 |
| A15 | 批量中一项失败 | 展示成功与失败；用户选择重试后只处理对应项 |
| A16 | 查询执行进度，或提交消息重复送达 | 查询已有任务，不无条件重复创建图像任务 |
| A17 | API 提交超时，执行结果未知 | 保存待核实状态，先查任务，不盲目重交 |
| A18 | 退出后恢复等待选图／执行中流程 | 会话、素材、选区、服务任务标识与待执行步骤可恢复 |
| A19 | 工具尚未接入／显式使用 Mock | 分别展示未接入／模拟状态，不声称真实生成成功 |
| A20 | 对结果要求保存、获取或继续调整 | 有真实文件时能定位／导出；新操作保留历史来源 |

离线测试使用模型替身、图像工具 Mock 和明确标记的测试素材，验证业务规则与恢复逻辑。真实千问验证需要可用鉴权配置，只验证主控行为；真实图像 API 和画质验收属于后续阶段。

模型评估重点是意图识别、该追问时追问、素材指代、选区解析、工具参数和多轮续接。结构合法不等于业务正确，两者分别验证并记录失败案例。

### 职责边界

| 部分 | 职责 | 本项目示例 |
| --- | --- | --- |
| `application` | 接收调用并组织返回 | 接收消息、附件与会话 ID，返回结构化回复 |
| `workflow` | 决定步骤与分支 | 输入齐全后生成，生成后等待选图 |
| `services` | 校验并落实业务规则 | 缺哪张图、选中了谁、再次换衣用哪张原图 |
| `providers` | 对接外部能力 | 千问理解需求，套图与试衣调用用户 API |
| `storage` | 保存并恢复业务记录 | 重启后找回任务、编号和选图状态 |

一次穿衣请求的处理顺序：统一入口 → 模型解析操作 → 业务代码解析编号并检查素材 → 流程节点调用穿衣工具 → 保存对应结果 → 返回回复。

节点调用业务服务，业务规则不集中堆在提示词或图连接代码中。供应商请求和响应转换集中在 `providers`，更换模型或图像 API 时尽量保持统一业务协议。

初期节点和数据库存取可以保持集中，内容增多后再细分。工程结构的确认不代表已经授权创建代码；实际开发仍按明确的启动指令和阶段计划执行。
